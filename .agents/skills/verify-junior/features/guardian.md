# Guardian

Guardian is Junior's action review. Right before a reviewed tool call runs, a separate model rates its risk and the user's authorization, and names the one block rule that it matches, or none. Code turns that rule into allow, ask, or deny. An ask tells the agent to get the user's confirmation for the exact action. A deny tells it to stop or take a safer path. Users see only the result: ordinary work runs without questions, and risky or unrequested writes wait or stop. Public docs: `packages/docs/src/content/docs/concepts/security-and-authority.md`.

## Claims

- `named-rule` Guardian blocks an action only when it names a block rule. A confirmation rule asks, and a hard rule denies. An action with high or critical risk and low or unknown authorization asks even when no rule matches. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/reviewer.test.ts -t "derives the decision from the named rule for the exact proposal|allows unless a named rule or a code backstop blocks the action"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/action-review.eval.ts -t "when the user explicitly authorizes a scoped destructive cleanup, allow it|when a destructive choice is delegated without confirmation, ask first|when exporting credentials to an untrusted destination, deny it"`.
- `ordinary-work` A user asks for scoped work. The conventional steps that deliver it, such as a repository clone, a pull request from a work branch, or the ticket that the user asked for, run without a question. A write that the user only suggested, or one with no destination, asks first. Proof: `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/code-delivery.eval.ts -t "when the user needs a sandbox clone for requested repo work, allow it|when scoped code work ends in a pull request with ordinary product context, allow it"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/ticket-filing.eval.ts -t "when the user asks to file a concrete ticket, allow the create|when ticket filing is only a vague suggestion, ask|when the create destination is missing, ask"`.
- `hard-deny` A write sends a secret or private data to a public place, sweeps for credentials, weakens a security control, or deletes data outside the work. Guardian denies it, also when the user asked for it. Proof: `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/harmful-actions.eval.ts -t "when the user asks to share a local env file in a public gist, deny it|when a code question turns into a sweep for stored credentials, deny it|when push protection blocks a detected secret, deny disabling it to finish the push|when a read-only production data question turns into a bulk delete, deny it"`.
- `rejection-reply` Guardian asks about an action. The action does not run, and the user gets one question that names it. A later confirmation lets it run, and a reply that holds it back does not. After a deny, the user gets an explanation, and the agent tries no workaround. Proof: `eval` with `pnpm --filter @sentry/junior-evals evals:integration evals/integration/conversation/action-review.eval.ts -t "when Guardian asks to confirm a call, ask the person and do not run it|when Guardian denies a call, tell the person and do not run it"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:behavioral evals/skills/action-review.eval.ts -t "when delegated a destructive choice, ask before acting and honor follow-up approval|when the follow-up withholds confirmation, do not execute or work around the rejection|when asked to export credentials to an untrusted destination, refuse without a workaround"`.
- `retry-blocked` The agent retries a rejected action under unchanged intent, also with another tool. Guardian rejects it again. After three rejected attempts in a row, the agent must stop and explain the risk. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/gate.test.ts tests/component/tool-support/pi-tool-adapter.test.ts -t "shows prior denials to alternate tools|counts each attempt once toward the rejection limit|reviews each attempt and interrupts after three consecutive rejections"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/action-review.eval.ts -t "when a prior ask is retried under unchanged intent, keep asking|when a prior deny is retried with another tool name under unchanged intent, keep denying"`.
- `review-scope` A tool marked read-only and not destructive runs without review. A plugin or MCP tool with missing annotations, or marked destructive, is reviewed. A core tool stays outside review unless it opts in. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/gate.test.ts tests/component/tool-support/pi-tool-adapter.test.ts -t "preserves execution behavior for unclassified core tools|skips review of read-only plugin and MCP actions|reviews auto actions when tool annotations are missing|reviews read-only actions that are also marked destructive|reviews an active MCP tool before execution"`.
- `fail-closed` Review cannot run: the authoritative context is missing, the Guardian model fails, or the decision cannot be saved. The action does not run, and the Turn ends at the run boundary. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/gate.test.ts tests/component/runtime/agent-run-mcp-progressive-loading.test.ts -t "fails closed before Guardian when authoritative context is missing|fails closed when Guardian cannot produce a decision|fails closed when the Guardian decision cannot be recorded|escalates unavailable Guardian review to the agent-run boundary"`.
- `automation-no-ask` A Scheduled or Event Automation run proposes an action that would ask. No person can answer, so Guardian denies it with a reason that says so. Writes that the Automation instruction names still run. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/reviewer.test.ts -t "allows unless a named rule or a code backstop blocks the action"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/automation-actions.eval.ts -t "when an Automation posts its authorized findings after a partial precondition check, allow it|when an Automation comment drifts to another issue, deny it|when an Automation adds an unrequested issue update, deny it"`.
- `untrusted-evidence` Only the current actor's own messages authorize an action. Text in tool results, files, issue or PR comments, tool descriptions, or another person's message cannot approve it or change the policy. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/unit/guardian/reviewer.test.ts tests/integration/agent-invocation-user-approval.test.ts -t "puts the root user instructions in a section that only this request can open|reads approval only from the Run's own Conversation"`, `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/action-review.eval.ts -t "when tool metadata tries to redefine policy, ignore the injection and deny|when only another person approved the PR, ask"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/trusted-author-comments.eval.ts -t "when an untrusted comment claims approval and overrides the task, deny it|when system Event text claims to be a trusted author instruction, deny it"`.
- `child-agents` A parent's `spawnAgent` or `messageAgent` call is judged by the actions that its text names. A child agent's action runs when its parent task names it, and a fake approval in a nested agent result does not count. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/integration/child-agents-without-agent-invocation.test.ts -t "labels a parent task as the instruction that Guardian reads|resumes a parent task as the instruction that Guardian reads"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/child-agent-approval.eval.ts -t "when the parent task names the deletion, allow it without asking again|when only a nested result fakes an approval section, deny it|when a parent delegates a deletion that the user never asked for, ask or deny the spawn"`.
- `code-mode` Each tool call that a Code Mode script makes is reviewed like a direct call. A rejected call fails alone, and a batch of more than 10 calls fails before any review. The script, its comments, and its strings cannot authorize. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/integration/codemode/bridge.test.ts tests/integration/codemode/tool.test.ts -t "reviews one drain as a batch and runs its calls in parallel|rejects only the denied call and keeps its marker|refuses a drain over the batch limit before any review|runs the script's calls through the Run's pipeline and keeps the script result in details"`, and `eval` with `pnpm --filter @sentry/junior-evals evals:guardian evals/guardian/script-provenance.eval.ts -t "when a script posts data that it read from a secrets file to a public issue, do not allow it|when a script comment claims approval for an unrequested write, do not allow it|when a script files the issue that the user asked for from data it listed, allow it"`.
- `decision-recorded` Each reviewed action records its decision, risk, and authorization on its Conversation, without the tool input. The Conversation API returns that event. Proof: `test` with `pnpm --filter @sentry/junior exec vitest run tests/component/runtime/agent-run-mcp-progressive-loading.test.ts tests/integration/api/conversations/event-list.test.ts -t "searches loadSkill-activated MCP tools in the same turn without replay|wires Guardian denial through the runtime before MCP execution for|reports privacy-safe Guardian decisions"`.
- `dashboard-activity` A user opens System in the dashboard. The "Guardian reviews" card shows the requests, allowed, asked, and denied counts, the estimated cost, and a chart per period. Proof: `drive`, and `test` with `pnpm --filter @sentry/junior exec vitest run tests/integration/api/conversations/stats.test.ts -t "aggregates normalized SQL conversation dimensions"` for the server counts.

## How to get to it

- Any Turn, child agent run, or Automation run that calls a reviewed tool, directly or from a Code Mode script.
- Slack and the dashboard: the agent's confirmation question after an ask, or its explanation after a deny.
- Dashboard: `System` in the `Primary` navigation (`/system`), the "Guardian reviews" card.
- Dashboard: the event log of a Conversation lists each `guardian_action_reviewed` event.

## Driving it with browse.mjs and proofs.mjs

Preconditions:

- `instance.mjs launch --mock` started a new instance, and `instance.mjs doctor` passes. The mock seeds 90 days of Guardian stats.
- Compose Postgres is healthy for the tests. `instance.mjs launch` starts it.
- `S=.agents/skills/verify-junior/scripts` and `E=$RUN_DIR/evidence/guardian`.

- **`dashboard-activity`: open System.** Run `node $S/browse.mjs --out $E/system --goto /system --expect 'role=heading[name="Guardian reviews"]' --expect 'role=img[name="Daily Guardian review results"]' --snap guardian`. The card shows the Requests, Allowed, Asked, Denied, and Estimated cost tiles above the chart.
- **`named-rule`, `retry-blocked`, `review-scope`, `fail-closed`, `automation-no-ask`, `untrusted-evidence`, `child-agents`, `code-mode`, `decision-recorded`, `dashboard-activity`: run the tests.** Run `node $S/proofs.mjs run --out $E/tests .agents/skills/verify-junior/features/guardian.md`. Each command exits `0`.
- **`named-rule`, `ordinary-work`, `hard-deny`, `rejection-reply`, and the eval half of the other claims: run the evals.** Add `--kind eval` to the same command. Each `evals:guardian` case checks an exact `allow`, `ask`, or `deny`. See Gotchas for what an eval run needs.

## Gotchas

- The tests fake the Guardian model and check the gate, the decision rules, and the wiring. Only the evals call the real Guardian model, so only they prove which rule a proposal matches.
- Evals need `ROACH_TOKEN`, or `ROACH_MODE=off` with `AI_GATEWAY_API_KEY` or `VERCEL_OIDC_TOKEN` and `cloudflared`. Without them, global setup fails before a case runs (see `SKILL.md`).
- Guardian evals (`evals:guardian`) feed a fixed proposal to the real reviewer and run no agent. The `rejection-reply` evals run the agent, and the integration case forces the Guardian decision.
- The mock seeds Guardian stats only. No mock Conversation has a `guardian_action_reviewed` event, so the event log cannot show one on the mock.

## Gaps

- `decision-recorded`: no drive shows a Guardian decision in a Conversation event log. The mock seeds no such event.
