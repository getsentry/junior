# Eval Taxonomy Migration Map

## Purpose

Map every current eval case to the capability spec it should verify, and mark the expected migration action before any renames or splits are made.

Legend:

- `keep`: scope/name are good enough for baseline.
- `rename`: behavior is valid, but suite/file/case naming should move closer to capability language.
- `split`: case proves more than one capability and should become smaller cases.
- `move`: case belongs under another suite/package.
- `replace`: behavior should be covered differently.
- `delete`: no distinct behavior contract.

## Follow-Up Spec Gaps

- `agent-turn-handling`: many passive, output, and role/addressee evals map here; this should stay a high-priority consolidated spec.
- `github-workflows`: GitHub evals should eventually move from generic skill workflow naming to provider-specific behavior requirements.
- `sentry-workflows`: Sentry eval should get a provider-specific workflow spec when Sentry behavior expands.
- `sandbox-file-tools` / `slack-tools`: coding file and canvas behavior need clear capability ownership if not already covered by existing tool specs.
